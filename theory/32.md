PART 14: INTERVIEW STRATEGY AND COMMON QUESTIONS
14.1 The 5-Step Interview Framework

WHEN GIVEN A CONCURRENCY PROBLEM:

STEP 1: IDENTIFY SHARED STATE
  "What data can multiple threads access?"
  "Which of these are modified by any thread?"
  Draw a box around shared mutable state.

STEP 2: IDENTIFY THE ACCESS PATTERN
  "Are there more readers or writers?" → Reader-Writer lock
  "Is there a producer and consumer?" → Queue + condition variable
  "Do threads need to sync at a point?" → Barrier/Latch
  "Do threads compete for limited resources?" → Semaphore
  "Just need atomic counter?" → atomic<int>

STEP 3: CHOOSE THE PRIMITIVE
  ┌────────────────────────────────────────────────────────┐
  │ Simple mutual exclusion → mutex + lock_guard           │
  │ Wait for condition → condition_variable                │
  │ Multiple readers → shared_mutex + shared_lock          │
  │ Simple counter → atomic<int>                           │
  │ Resource pool limiting → semaphore                     │
  │ Task with return value → future/promise/async          │
  │ Multiple mutex → scoped_lock                           │
  │ Single-use sync point → latch                          │
  │ Repeated sync point → barrier                          │
  └────────────────────────────────────────────────────────┘

STEP 4: IMPLEMENT WITH RAII
  Always wrap locks in lock_guard/unique_lock/scoped_lock
  Never manually unlock (exception safety!)

STEP 5: CHECK FOR:
  ✓ Data races (every shared mutation protected?)
  ✓ Deadlock (lock ordering? scoped_lock for multiple?)
  ✓ Starvation (fairness? condition predicate correct?)
  ✓ Spurious wakeups (predicate in wait?)
  ✓ Lost notifications (condition checked before wait?)
  ✓ Exception safety (RAII everywhere?)
  ✓ Shutdown/cleanup (how does it terminate gracefully?)
